What this course is

This project is a small but complete data platform. It downloads public drone flight logs from PX4 Flight Review, lands the raw files in object storage, turns them into tables, cleans and models them with SQL, tests them, and publishes dashboards. All of it runs on your laptop.

Each lesson takes one piece of it and teaches two things at once:

  • The data engineering idea, explained from scratch: why landing zones exist, what a table format is, why ingestion must be idempotent, what "grain" means…
  • How this pipeline does it: the files, the UI, the data, and the commands that show it working.

You already know SQL and Python, so the course doesn't explain those. It does explain every DE concept the first time it appears; the glossary collects them all.

Safety rules

Everything in this course is reversible as long as you follow these rules.
  1. Never run make reset. It deletes every volume: all data, the Airflow history and the catalog. Nothing in the course needs it.
  2. Keep downloads small. A full day of flight logs is ~9 GB. When you trigger ingestion, always pass {"max_ulogs": 2} to {"max_ulogs": 5}. Never unpause px4_ingest_daily unless PX4_MAX_ULOGS_PER_RUN is set in .env.
  3. Experiment in the sandbox schema, created in lesson 5. Don't create tables in bronze, silver, gold or audit.
  4. Finish every lab with its Undo step, then check that git status shows no changes you didn't intend.
  5. Leave the DAG states as you found them: only px4_transform is unpaused (active).

Lesson 1 · 45 min

The big picture

What problem this pipeline solves, how data flows through it, and the vocabulary every later lesson uses. You'll finish by following one real flight from the API all the way to a dashboard.

You will
  • Explain the difference between a data lake, a warehouse and a lakehouse.
  • Name the four data layers (landing, bronze, silver, gold) and what each one is for.
  • Trace a single flight log through every layer with SQL and S3 commands.

The problem

PX4 is the most widely used open-source drone autopilot. Pilots upload their flight logs to a public site, PX4 Flight Review. That data could answer real questions: which vehicle types fly most, in which flight modes, on which firmware, and how often they crash. But it's scattered across ~477,000 index records and one binary file per flight.

Answering those questions once is a script. Answering them every day, reliably, as new data arrives is data engineering. That means downloading politely, never losing or duplicating data, cleaning known defects, testing the results, and publishing only numbers you trust.

Concepts

Lake, warehouse, lakehouse

  • A data warehouse (e.g. Snowflake, BigQuery) stores tables in its own format and runs SQL on them. You get schemas, transactions and fast SQL, but the data lives inside that one product.
  • A data lake is files (CSV, JSON, Parquet) in cheap object storage like S3. It's open and cheap, but "a folder of files" has no schema, no transactions and no history.
  • A lakehouse keeps the files in object storage and adds an open table format (Apache Iceberg here) that turns them into real tables. Any engine can query them: Trino, Spark, DuckDB… This project is a small lakehouse.

ELT, batch

ETL transforms data before loading it. ELT loads it raw first and transforms it afterwards with SQL, inside the platform. ELT keeps the raw data, so when a cleaning rule turns out to be wrong, you fix the SQL and rebuild; nothing has to be downloaded again. This pipeline is ELT.

It's also batch: once a day it processes the previous day's uploads. (The alternative, streaming, processes each event as it arrives; nothing here needs that.)

Exercise: trace one flight

Follow one real flight log through every layer. Run each step, then compare with the answer.

1. Pick a flight. Take the most recently parsed log:

make trino SQL="SELECT log_id, log_date FROM audit.ulog_downloads WHERE status = 'parsed' ORDER BY event_at DESC LIMIT 1"

one row, e.g. "0562512f-8c77-4269-8b39-797ae9cf0935","2026-10-14". Use your log_id and log_date below.

2. Landing. The raw flight file, as downloaded:

make s3 ARGS="ls s3://landing/px4/ulog/log_date=2026-10-14/" | grep 0562512f

2026-10-15 06:03:54 11833376 0562512f-….ulg (a 12 MB binary file).

3. Bronze. The index record (raw JSON) and the telemetry rows parsed from the file:

make trino SQL="SELECT log_date, _change_type, substr(payload, 1, 100) FROM bronze.logs_index_raw WHERE log_id = '0562512f-8c77-4269-8b39-797ae9cf0935'"

one insert row whose payload starts {"airframe_name":"Generic Quadcopter",…, then "317" telemetry rows (one per second of flight).

4. Silver. The cleaned, modeled row for this flight:

make trino SQL="SELECT uploaded_date, vehicle_class, duration_s, is_simulation, has_telemetry FROM silver.fct_flight WHERE log_id = '0562512f-8c77-4269-8b39-797ae9cf0935'"

"2026-10-14","multirotor","316","false","true".

5. Gold. This flight is now one of the logs counted in its class and month:

make trino SQL="SELECT month, vehicle_class, logs, round(flight_hours, 1) FROM gold.mart_flights_by_class_month WHERE month = date '2026-10-01' AND vehicle_class = 'multirotor'"

"2026-10-01","multirotor","4434","205.4".

6. Dashboard. On Fleet overview, the "Flight Hours per Month, by Vehicle Class" chart shows that same multirotor value for the latest month.

What did this show?

One flight became: a file (landing) → a JSON row plus ~300 telemetry rows (bronze) → one clean row with derived columns such as vehicle_class and is_simulation (silver) → one unit inside an aggregate (gold) → a number on a chart. Notice that the names change on the way: log_date in bronze becomes uploaded_date in silver, because it's the upload date, not the flight date (lesson 3).

If step 2 printed nothing, the raw file had already expired. Landing keeps raw flight files for one day (lesson 4); bronze keeps the parsed data forever.

Exercise. Which containers store data, and which only process it?

Show answer

Store: rustfs (every file: raw data, all table data and metadata, reports) and postgres (Lakekeeper's catalog and Airflow's run history). Both keep it in Docker volumes.

Process only: airflow (runs the code), trino (runs SQL), lakekeeper (answers catalog requests; its state is in Postgres), charts (renders dashboards). Stop any of these, and no data is lost.

Quiz

Which layer is allowed to change existing rows?

Landing is immutable and bronze is append-only, which is what makes them a safe source to rebuild everything else from.

Why ELT rather than ETL here?

With ETL, a bug in the transform corrupts what you stored. With ELT, the raw data in bronze is untouched.

What makes this a lakehouse rather than a plain data lake?

A lake also has S3 and Parquet. The table format is what turns files into tables.

Containers and Compose

The platform is 8 containers described in one file. This lesson covers how they find each other, where data survives restarts, and how Compose starts everything in the right order.

You will
  • Tell an image from a container, and a container from a volume.
  • Explain how containers reach each other by name.
  • Read the start order from depends_on, and see what happens when a service disappears.

Concepts

  • Image: a read-only template (an OS, Python, the installed code). Container: a running instance of an image. You can delete and recreate containers freely.
  • Volume: storage that outlives containers. Postgres and RustFS keep their data in named volumes, so make down loses nothing; only make reset (down -v) deletes volumes.
  • Compose describes a set of containers (services) in one YAML file and puts them on a private network. On that network each service is reachable by its name: Airflow talks to http://trino:8080, not to an IP.
  • Ports: 127.0.0.1:8085:8080 publishes the container's port 8080 as port 8085 on your machine, only on localhost. Containers use the internal port; your browser uses the published one.
  • Healthchecks are commands Docker runs periodically to decide whether a container is healthy, not merely running (e.g. "does Postgres answer a query?").
  • depends_on orders startup. condition: service_healthy waits until a container is healthy. condition: service_completed_successfully waits until a one-shot job has finished with exit code 0.
  • Secrets live only in .env (never committed). Compose substitutes ${VAR} from it.
postgres ──healthy──▶ lakekeeper-migrate ──exit 0──▶ lakekeeper ──healthy──┐
rustfs ──healthy─────────────────────────────────────────────────────────┴─▶ setup ──exit 0──▶ trino ──healthy──▶ airflow, charts

setup is a one-shot job: it creates the buckets, lifecycle rules, warehouse and namespaces through each tool's API, prints what it did, and exits. It's idempotent: running it again changes nothing that's already right.

  • Makefile and .env.example: the shortcuts and the configuration template.

Exercise. Why does trino wait for setup to finish before it starts?

Show answer

Trino's Iceberg catalog points at Lakekeeper's warehouse px4 (see infrastructure/trino/catalog/iceberg.properties). setup creates that warehouse and the namespaces. If Trino started first, on a fresh install its first queries would fail with "warehouse not found".

Exercise. You run make down, then make up. Is your data still there? What about after make reset?

Show answer

After down/up, yes: the containers are recreated, but the volumes holding the data are kept. make reset runs down -v, which deletes the volumes and so every table, file and run history.

A service disappears

  1. Stop the SQL engine: docker compose stop trino
  2. Try a query: make trino SQL="select 1". It fails: the container isn't running.
  3. Ask dbt Charts to render a board from scratch: make dct ARGS="render charts/pipeline_health.yml --format text". Look for Failed to resolve 'trino': a stopped container's name disappears from the network.
  4. Open Fleet overview. It still shows numbers, with "Data as of …" at the bottom: the dashboard server keeps its last results. Your portal page shows Trino as "no response".
  5. Undo: docker compose start trino, then make ps until trino is (healthy) (about 10 s), and make trino SQL="select 1" prints "1".

Quiz

Inside the Docker network, how does Airflow reach Trino?

Service names resolve on the Compose network, and containers use the internal port. localhost:8085 is the published port for your machine; inside a container, localhost is the container itself.

Why does setup show Exited (0) in make ps?

Exit code 0 means success. Services that depend on it with service_completed_successfully only start after that.

What does a healthcheck add over "the container is running"?

A process can be running while still initializing or broken. depends_on: service_healthy waits for the real thing.

Lesson 3 · 50 min

The source and ingestion design

Before writing any code, a data engineer studies the source: how it's served, how it changes, and what's wrong with it. Those answers decide how ingestion must work.

You will
  • Use HTTP conditional requests (ETag, 304) and explain why they matter.
  • Explain idempotency and change detection by hashing.
  • Measure real data defects in bronze with SQL.

Concepts

The source

  • The index: GET https://review.px4.io/dbinfo redirects to one gzipped JSON file (~32 MB) holding every public log since 2016: ~477,000 records with 26 fields each. There are no filters and no pagination; the file is regenerated once a day, just after midnight UTC.
  • Flight files: each record has a download_url to a binary ULog file (median 6.5 MB, mean 18 MB). Telemetry such as position, altitude and battery exists only inside these files.

Don't download what you already have: conditional GET

The server sends an ETag (a fingerprint of the file). The client stores it and sends it back as If-None-Match. If the file hasn't changed, the server answers 304 Not Modified with an empty body, so 32 MB becomes 0 bytes.

Idempotency

An operation is idempotent if running it twice has the same effect as running it once. Pipelines fail and get retried all the time, so every step must be safe to re-run:

  • Re-downloading the same index: 304, nothing changes.
  • Re-loading the same snapshot: 0 new rows.
  • Re-fetching a ULog that's already in landing: skipped.

Change detection with a hash

Each day's file is yesterday's plus ~500–600 new logs, and occasionally an edited one (a rating added later). Reloading 477k rows daily would be wasteful. Instead, the loader computes payload_hash = sha256(canonical JSON) for each record and compares it with the latest hash stored in bronze for that log_id:

new log_id               → insert, _change_type = 'insert'
same log_id, new hash    → insert, _change_type = 'update'   (history is kept)
same log_id, same hash   → skip

Bronze is append-only: an edited record adds a new row and never overwrites the old one. Silver later keeps only the latest version (lesson 10). The first load (the bootstrap) only takes records uploaded on or after INDEX_START_DATE (2025-01-01).

Profiling: know the defects

Profiling the source (Phase 1, reports in docs/reports/) found real defects that silver must clean:

  • wind_speed = -1 means "no data" (~99 %).
  • airframe_type is sometimes an integer instead of a name.
  • duration_s has overflowed counters (values up to 1.8e13 seconds).
  • ~8 % of logs come from simulators (sys_hw contains SITL).
  • log_date is the upload date, not the flight date.

  • ingest/src/drone_ingest/index.py: snapshot_index (the conditional GET) and load_index (the hash diff).
  • docs/reports/dbinfo_profile.md: the full profile of every field.
  • docs/reports/ulog_sizes.md: ULog sizes, which drove the 1-day raw window.
  • CLAUDE.md, sections 3 and 4: the API contract, the defects and the daily diff.

An idempotent download

  1. Run the ingestion step that downloads the index, inside the airflow container (the same command the DAG runs):
    docker compose exec airflow /opt/ingest-venv/bin/drone-ingest snapshot-index
  2. Read the log lines: it sends If-None-Match with the ETag of the last loaded snapshot, gets 304 Not Modified, and prints the JSON summary {"command": "snapshot-index", …, "status": "not_modified", …}.
  3. The pipeline recorded what it did. Read its audit table:
    make trino SQL="SELECT entity, status, bytes, started_at FROM audit.ingestion_runs ORDER BY started_at DESC LIMIT 5"
    Your run is at the top: index_snapshot, not_modified, 0 bytes.
  4. Undo: nothing to undo. The step was idempotent: no file landed and no table changed except one audit row, which is exactly what should happen.

Quiz

The server answers 304 to a conditional GET. What did the client download?

304 has no body. HTTP has no "only the changes" mode for this file, which is why the loader diffs records by hash.

A log's rating is edited upstream. What happens in bronze on the next load?

The hash changed, so a new version is appended. Bronze keeps history; silver picks the latest version per log_id.

Why does idempotency matter so much in pipelines?

Retries are normal: networks fail, tasks get killed. If re-running a step is always safe, recovery is just "run it again".

Lesson 4 · 40 min

Object storage and the landing zone

Every byte in this platform lives in S3-compatible object storage (RustFS), from raw downloads to tables to reports. This lesson covers how object storage differs from a filesystem, why raw files land untouched, and how old files expire by themselves.

You will
  • Explain buckets, keys and prefixes, and why "folders" are an illusion.
  • Read the landing layout and a manifest, and say why the manifest is written last.
  • Watch a lifecycle rule delete an object with no job at all.

Concepts

  • Object storage stores objects (bytes + metadata) under a key inside a bucket. The namespace is flat: px4/ulog/log_date=2026-10-14/x.ulg is one key, and the slashes are just characters. Tools show prefixes as folders for convenience.
  • Objects are written whole and never edited in place: there's no "append" and no cheap "rename". That's why table formats (next lesson) write new files instead of changing old ones.
  • It's cheap, practically unlimited, and accessed over HTTP with the S3 API. RustFS implements the S3 API locally; the same code would work against AWS S3.
  • Path-style addressing (http://rustfs:9000/landing/key) instead of virtual-host style (http://landing.rustfs:9000/key), because landing.rustfs doesn't resolve on the Compose network.

The landing zone

Landing holds source files exactly as downloaded. Keeping that raw copy lets you:

  • re-parse after fixing a bug, without hitting the API again;
  • audit what the source actually sent;
  • keep "download" and "load" as separate, independently retryable steps.
s3://landing/px4/index/snapshot_date=2026-10-15/run_id=…/dbinfo.json.gz   ← the data
                                                         /_manifest.json  ← written LAST
s3://landing/px4/ulog/log_date=2026-10-14/<log_id>.ulg

key=value segments (snapshot_date=…) are a common convention ("Hive-style"). They make keys self-describing and easy to filter by prefix.

The manifest: a commit marker

A big upload can fail halfway. The downloader writes the data file first, then a small _manifest.json with the ETag, size, record count and sha256. Readers only trust snapshots that have a manifest, and load-index recomputes the sha256 before loading. A half-written file is therefore never loaded.

Lifecycle rules: retention without a job

Raw ULogs are ~9 GB per day, so they can't be kept forever. Instead of a cleanup job, the buckets carry lifecycle rules: "delete objects under this prefix N days after they were written". The storage system applies them by itself, with a background scanner.

  • landing/px4/ulog/: 1 day.
  • landing/px4/index/: 7 days.
  • reports/: 30 days.

Deletion is asynchronous (it happens some time after an object becomes eligible), so the ingestion code still checks free disk before downloading.

Lesson 5 · 50 min

Table formats: Apache Iceberg

A folder of Parquet files isn't a table. This lesson shows what Iceberg adds (schemas, atomic commits, snapshots, time travel, partitioning) by building a small table in your own sandbox and looking at the files it writes.

You will
  • Explain the Iceberg file tree: metadata file → manifest list → manifests → data files.
  • Use snapshots, time travel and schema evolution.
  • Read Iceberg's metadata tables ($snapshots, $files, $partitions, $history).

Concepts

Why files alone aren't a table

Picture a table as a folder of Parquet files. A writer adds 3 new files while a reader is listing the folder, so the reader sees half a write. A failed job leaves stray files behind. Deleting rows means rewriting files while others read them. There's no schema to check against, and no way back if a bad load lands. A table format fixes all of this with metadata that says exactly which files make up the table right now.

catalog ──▶ metadata.json  (schema, partition spec, list of snapshots, current snapshot)
                 └─▶ manifest list   (one per snapshot: which manifests)
                        └─▶ manifests (which data files, with per-column min/max stats)
                               └─▶ data files (Parquet)
  • Commits are atomic. A writer writes new data files and new metadata, then asks the catalog to swap the table's pointer from the old metadata.json to the new one. Readers see the whole commit or nothing.
  • Snapshots. Every commit creates a snapshot: the complete list of files at that moment. Old files aren't deleted, so you can query old snapshots. That's time travel.
  • Schema evolution. Adding or renaming a column changes metadata only; old files are read with the new schema (missing columns read as null).
  • Hidden partitioning. The table is declared partitioning = ARRAY['month(uploaded_date)'], and Iceberg groups files by month. Queries just filter on uploaded_date, and files from other months are skipped (lesson 7). Users never deal with a "month" column.
  • Min/max statistics in the manifests let engines skip files whose values can't match a filter.

  • ingest/src/drone_ingest/catalog.py: the bronze and audit table definitions (PyIceberg), including partitioning by month(log_date), and an append that retries when another writer committed first.
  • infrastructure/trino/catalog/iceberg.properties: how Trino reaches Iceberg (the REST catalog plus S3).

Lesson 6 · 40 min

The catalog: Lakekeeper

The catalog decides which metadata file is the table. This lesson covers how engines talk to it, how a browser can read a table safely, and two safety nets on top: soft delete and protection.

You will
  • Explain what a catalog stores, and why every engine must share one.
  • Call the Iceberg REST API and find a table's current metadata file.
  • Drop a table and restore it; protect a table and watch a DROP get refused.

Concepts

  • The catalog maps namespace.table to the location of its current metadata.json. To commit, a writer says "move the pointer from A to B". If someone else committed first (the pointer is no longer A), the catalog refuses and the writer retries. That compare-and-swap is what makes concurrent writes safe.
  • One catalog, many engines. Here, Trino (SQL, dbt, dashboards), PyIceberg (the ingestion code) and DuckDB (in the browser) all use the same catalog, so they all see the same tables.
  • The Iceberg REST catalog is an open HTTP API for this. Lakekeeper is a server that implements it, and it keeps its own state (warehouses, namespaces, pointers) in PostgreSQL.
  • Warehouse → namespace → table. Warehouse px4 stores data under s3://lakehouse/. Namespaces (bronze, silver, gold, audit) are like schemas.
  • Two APIs: /catalog/v1/… is the standard Iceberg API that engines use; /management/v1/… is Lakekeeper's own API for warehouses, soft delete and protection.
  • Vended credentials. The catalog can hand a client short-lived S3 keys scoped to one table's files. That's how DuckDB in your browser reads a table without knowing the real S3 keys.
  • Soft delete: a dropped table is hidden but kept for 7 days and can be restored. Protection: a protected table can't be dropped at all until protection is turned off.

  • infrastructure/setup/setup.py: setup_lakekeeper() (bootstrap, warehouse, soft-delete profile) and setup_namespaces().

  • DECISIONS.md: D-007 (why Lakekeeper) and D-010 (soft delete, and why protection isn't automated).

The SQL engine: Trino

Concepts

  • Storage and compute are separate. The data lives in RustFS and the table metadata in Lakekeeper. Trino only computes: it plans a query, reads the files it needs, and returns the result. You could delete the Trino container and lose nothing, or point a second engine at the same tables.
  • Catalogs and connectors. Each Trino catalog is a connector plus its config. Here, iceberg is the lakehouse (via Lakekeeper) and tpch is a built-in generator of benchmark data. A query can even join across catalogs.

  • Memory limits. Trino holds intermediate results in memory. Here it's capped (2 GB heap, 1 GB per query) to fit an 8 GB laptop.

Lesson 8 · 50 min

The ingestion code: drone_ingest

Ingestion is the code that talks to the outside world, so it's where most failures happen. This lesson covers the patterns that make it safe: small commands with machine-readable results, validation with a dead-letter table, audit logs, polite retries and guards.

You will
  • Explain why the code is split into pure functions and I/O, and how that makes it testable.
  • Read the audit and rejection tables to answer "what did the pipeline do?".
  • Trigger a guard and a failing test on purpose, then undo both.

Concepts

Small commands, structured results

drone_ingest is one CLI with six commands, one per step:

snapshot-index ─▶ load-index                         (the index)
plan-ulogs ─▶ fetch-ulogs (per batch) ─▶ parse-ulogs (per batch)   (flight files)
init-tables                                            (create missing tables)

Each command prints one JSON summary as its last line on stdout, e.g. {"command": "plan-ulogs", "entries": 2, "batches": 1, "out": "…/plan.json"}. Logs go to stderr, each tagged with run_id=… cmd=…. Airflow stores that last line as the task's result (XCom), and the next task reads it. The CLI also runs on your laptop, so every step can be tested outside Airflow.

Pure functions vs I/O

Diffing records, validating them and parsing a ULog are pure functions: data in, data out, no network, no S3. Downloading and writing tables are I/O. Keeping them apart means the tricky logic is tested in a second with small fixture files (ingest/tests/fixtures/), while the I/O stays thin.

Validate, don't crash: the dead-letter table

A contract (a pydantic model) checks only the fields the pipeline relies on: log_id must be a UUID, log_date a date, durations integers. A record that fails is not dropped silently, and it doesn't crash the load either. It goes to bronze.rejected_records with a reason (invalid_log_id, missing_log_date, …). Everything else in the record stays raw for silver to clean.

Audit and event logs

  • audit.ingestion_runs: one row per command run (what, status, counts, bytes, duration).
  • audit.ulog_downloads: an append-only event log per flight file: downloaded → parsed, or rejected (terminal: not_found, too_large, parse_error…), or failed (retried next run). A file's current state is its latest event. That's how the planner knows what's left to do.

Be polite, be safe

  • Retries with backoff, following PX4's own download script: on 503, wait Retry-After or 30·2n s (max 300); on 403/444 (blocked), abort the whole run; on 404, skip; on anything else, retry up to 5 times. Every request sends an identifying User-Agent.
  • Bounded concurrency: 4 downloads at a time, in batches of 50.
  • Verify what you got: a truncated ULog parses without any error, so fetch compares the downloaded size with Content-Length.
  • Disk guard: before a batch, compare free disk with the batch's total size, and refuse if less than MIN_FREE_DISK_GB would remain.
  • Concurrent commits: parallel tasks append to the same Iceberg table. When the catalog refuses a commit because someone else committed first, append retries.

Parsing: from 100 Hz to 1 Hz

A ULog has dozens of topics, each a time series at its own rate. The parser averages each second (and keeps the last value for states such as arming), producing one telemetry row per second. Missing topics become null columns. Timestamps are microseconds since boot, so UTC comes from the GPS topic when there's a fix.

  • catalog.py and audit.py: table definitions, retried appends, audit rows.

Orchestration: Airflow

An orchestrator decides what runs, when, in which order, and what happens when something fails. It doesn't do the work itself. This lesson walks through the daily ingestion DAG and makes it fail on purpose.

You will
  • Read a DAG: tasks, dependencies, schedule, params and templates.
  • Explain short-circuiting, trigger rules, dynamic task mapping and retries with backoff.
  • Trigger runs safely, find a task's rendered command and its result (XCom), and watch retries exhaust.

Concepts

  • DAG (directed acyclic graph): tasks plus the dependencies between them (a >> b means "b after a"). It's defined in Python, but the file only declares the graph; it doesn't run the work.
  • Operator: a template for a task. BashOperator runs a shell command (here, the drone-ingest CLI); @task turns a Python function into a task.
  • The moving parts: the DAG processor parses DAG files; the scheduler decides what's due; the executor runs tasks (LocalExecutor: as processes in the same container); the API server serves the UI. Here airflow standalone runs all four in one container.
  • Schedule: 0 2 * * * in America/Hermosillo (09:00 UTC), when yesterday (UTC) is complete. catchup=False means missed days aren't replayed one by one. But unpausing a DAG runs its latest missed slot immediately; that's why the course always caps downloads.

Transformation: dbt

The "T" of ELT. You write SELECT statements; dbt works out the order, turns each SELECT into a table, tests the results and documents everything. This lesson covers how a project is wired and what dbt actually sends to Trino.

You will
  • Explain source(), ref() and the lineage graph dbt builds from them.
  • Tell the materializations apart (table, incremental merge/append, seed, snapshot), and why each model uses the one it does.
  • Read compiled SQL, preview a model, and change one end to end.

Concepts

  • A model is a SELECT in a .sql file. dbt wraps it in the DDL/DML needed to persist it (CREATE TABLE … AS, MERGE…) and runs it on Trino. You never write INSERT or DROP.
  • source('bronze', 'telemetry_raw') points at a table dbt reads but never writes. ref('fct_flight') points at another model. From these calls dbt builds the lineage graph, so it knows the run order and what's downstream of a change.
  • Materializations (how a model is persisted):
    • table: rebuilt from scratch each run. Here with on_table_exists: replace, so dbt issues CREATE OR REPLACE TABLE and each run becomes a new Iceberg snapshot of the same table.
    • incremental: only processes new data. stg_logs uses merge on log_id (an edited index record replaces its row). stg_telemetry and stg_log_messages use append (those rows never change). Both read only bronze rows with _ingested_at newer than the latest already in the target.
    • seed: a small CSV lookup table versioned in git (flight mode names, vehicle class mapping…).
    • snapshot: keeps history of changing rows (SCD2, next lesson).
  • Jinja and macros: SQL files are templates. {{ real_flights() }} expands to not is_simulation; {% if is_incremental() %} adds the "only new rows" filter after the first run.
  • dbt build runs seeds, models, snapshots and tests in lineage order, and skips everything downstream of a failure. Selectors: -s fct_flight (one model), -s +fct_flight (it and everything upstream), -s tag:gold.

Lesson 11 · 45 min

Data modeling

Modeling decides what a row means, which questions are easy to answer, and where business rules live. This lesson covers the silver and gold layers: cleaning, facts and dimensions, grain, and history.

You will
  • Explain what silver cleans, and why rules belong there rather than in each query.
  • Read a star schema, and prove a table's grain with SQL.
  • Query SCD2 history, and see why a modeled mapping beats ad-hoc filters.

Concepts

Silver: clean once, in one place

Silver applies every cleaning rule from lesson 3, as SQL anyone can read:

  • types from JSON strings;
  • sentinels to null (wind_speed = -1);
  • impossible values to null (durations outside 1–86,400 s);
  • honest names (log_date → uploaded_date);
  • the latest version per log_id;
  • derived columns (vehicle_class from a seed mapping, is_simulation, fw_major_minor).

Every consumer then gets the same answer.

Facts and dimensions (a star schema)

  • Facts record events and measurements: fct_flight (one row per flight), fct_mode_segment (one row per flight × flight-mode segment), fct_telemetry_1min (one row per flight × minute).
  • Dimensions describe the things facts refer to: dim_vehicle, dim_flight_mode, dim_error_label, dim_date.
              dim_vehicle            dim_date
                   │ vehicle_uuid        │ uploaded_date
                   ▼                     ▼
dim_flight_mode ─▶ fct_mode_segment ◀── fct_flight ──▶ fct_telemetry_1min
     mode_id            (log_id)        (log_id)            (log_id)

Grain

A table's grain is what one row represents. Get it wrong and every sum double-counts. State it ("one row per flight"), then test it: log_id is unique and not_null in fct_flight.

History: SCD type 2

A vehicle can change its airframe or firmware. Overwriting the row loses the past; SCD2 (slowly changing dimension, type 2) keeps every version with dbt_valid_from / dbt_valid_to. The current version has dbt_valid_to IS NULL. A dbt snapshot does this, comparing chosen columns on each run.

Gold: built for one purpose

Gold marts are small aggregates shaped for a dashboard, with a contract (fixed columns and types, lesson 13). They exclude simulator logs through one macro, real_flights(), so the rule can't be forgotten in one place and applied in another.

dbt inside Airflow: Cosmos and data-aware scheduling

The transform DAG has no clock. It runs when bronze changes, and every dbt model becomes its own Airflow task. This lesson covers why that matters, and shows a failing test stopping bad data before it's published.

You will

Concepts

One task per model

Running dbt build as one big task works, but when it fails you see only "dbt failed", and a retry reruns all 81 nodes. Cosmos reads the dbt project and renders each model as Airflow tasks: silver.stg_logs.run, then silver.stg_logs.test with its tests. A model with no tests of its own is a single …_run task. You can see which model failed, read its log, and clear just that task.

A test that references two models (e.g. a relationship from fct_flight to dim_vehicle) would race if attached to only one of them, so Cosmos detaches it into its own task that waits for both parents (names ending in _test). In total: 49 tasks.

Data-aware scheduling with assets

An asset is a named piece of data, here an Iceberg table URI. Tasks declare the assets they update (outlets). When one succeeds, Airflow records an asset event, and any DAG scheduled on that asset starts.

px4_ingest_daily                                    px4_transform (schedule = any of the 3)

  • max_active_runs=1: two transform runs never write the same tables at once.
  • Events that happen while the consumer DAG is paused don't queue a run.

Visualization and publishing: dbt Charts

The dashboards are code too: YAML files next to the dbt models, validated against them, rendered on every run and published to S3. This lesson covers how a board is built and how the publish gate keeps a broken one from shipping.

You will
  • Read a board: source, variables (filters), queries, charts.
  • Tell offline validation from execution checks, and what the publish gate requires.
  • Break a board and watch the gate refuse it.

Concepts

  • Dashboards as code: each board is a YAML file in dbt/charts/, versioned and reviewed like any code. Queries use {{ ref('mart_…') }}, so they're tied to dbt models, and they read only gold.
  • Anatomy: source (the connection, reusing the dbt profile) · variables (filters, e.g. upload period, vehicle class) · queries (SQL; filters through filter() macros) · charts (type, x, y, color, labels).
  • Two kinds of checks:
    • Offline validation (dct validate --strict) compares each query's columns with the dbt model's columns, without touching the database. That only works when every column is qualified (m.logs, not logs), and it can't analyze queries with filter macros.
    • Execution (dct render) runs every query on Trino, catching what the offline check can't.
  • The publish gate (check_charts.py) requires both to pass. Warnings that only mean "not enough data yet" (an empty chart on a young install) are reported but don't block.
  • Two outputs: live boards (dct serve on port 8088, which keeps serving its last results with "Data as of…" if Trino is down; lesson 2), and static HTML/PDF copies rendered by px4_transform and uploaded to s3://reports/<day>/, where a lifecycle rule keeps them 30 days.

Lesson 15 · 40 min

Operations: keeping it healthy

Running a platform every day creates small files, old snapshots and raw data that must eventually go. This last lesson covers maintenance, retention and recovery, and cleans up your sandbox.

You will
  • Explain compaction, snapshot expiry and orphan-file removal, and run them.
  • Know how long each kind of data is kept, and why.
  • Know how to recover from the common accidents.

Concepts

  • Compaction (optimize) rewrites a partition's small files into fewer large ones. The data doesn't change; queries open fewer files. It commits a replace snapshot.
  • Snapshot expiry (expire_snapshots, 7 days) forgets snapshots older than the threshold and deletes files only they referenced. That's the trade-off: time travel reaches back 7 days, and storage doesn't grow forever.
  • Orphan files (remove_orphan_files, 7 days) are files no snapshot references, e.g. from a commit that failed and was retried. They're safe to delete once old enough that no write in progress could still be using them.

Retention at a glance

DataKeptBy
Raw flight files (landing/px4/ulog/)1 dayRustFS lifecycle rule
Raw index snapshots (landing/px4/index/)7 daysRustFS lifecycle rule
Reports (s3://reports/)30 daysRustFS lifecycle rule
Old Iceberg snapshots (time travel)7 dayspx4_maintenance, weekly
Dropped tables7 daysLakekeeper soft delete
Bronze, silver, gold dataForeverNothing deletes it

Recovery recipes

  • A table was dropped → Lakekeeper → Deleted → Restore (lesson 6).
  • Silver or gold is wrong → fix the SQL, rebuild from bronze (make dbt ARGS="build -s model+ --full-refresh" for incremental models; lesson 13).
  • Yesterday's ingestion failed → trigger px4_ingest_daily with {"day": "…"}; it skips what's already done (lesson 9).
  • A container died → make up; data lives in volumes (lesson 2).
  • "Does the whole thing still work from zero?" → the smoke test from a clean clone (README → "Smoke test").

In this repo

  • dags/px4_maintenance.py: lists every table, then runs the three procedures per table through Trino, at most 2 tables at a time, and returns what it compacted.
  • infrastructure/setup/setup.py: the retention rules and the soft-delete period, set once.

Run it

Count data files per table, run maintenance, count again:

one line per table, e.g. "telemetry_raw","9", "log_messages_raw","9", "logs_index_raw","23".

make airflow ARGS="dags unpause px4_maintenance"
make airflow ARGS="dags trigger px4_maintenance"

a run of about 25 s: iceberg_tables, then one mapped maintain task per table. Each task's Storage → XCom says whether it compacted ({"table": "bronze.telemetry_raw", "compacted": true, "files_removed": …, "files_added": …}). Then pause it again: make airflow ARGS="dags pause px4_maintenance".

Run the file count again: e.g. 9 → 5, 9 → 5, 23 → 22. That's one file per partition: telemetry_raw is partitioned by upload day and had 5 days. Lakekeeper's Health tab for telemetry_raw now reports fewer, larger files.

Exercise. Can you time-travel to a snapshot from 8 days ago? Why not, and what would you change to keep 30 days?

Show answer

No. The weekly expire_snapshots(retention_threshold => '7d') forgot every snapshot older than 7 days and deleted the files only they referenced. To keep 30 days, raise RETENTION in dags/px4_maintenance.py. The cost is storage: every replaced file is kept for 30 days instead of 7.

Exercise. Which loss would be worse: the rustfs-data volume or the postgres-data volume?

Show answer

Both are serious, in different ways. Losing rustfs-data loses every byte of data. Losing postgres-data loses the catalog and Airflow's history: the Parquet files would still be in RustFS, but no engine would know which files form which table or which snapshot is current. The catalog is small, but it is critical state. Production platforms back up both.

Clean up your sandbox

make trino SQL="DROP TABLE sandbox.flights"
make trino SQL="DROP SCHEMA sandbox"

DROP TABLE; then the schema drop fails with Namespace with name 'sandbox' is not empty. The dropped table is still soft-deleted, so it can be restored for 7 days, and it counts as content. Leave the empty sandbox schema; after 7 days DROP SCHEMA sandbox succeeds. This is one consequence of soft delete you'll meet in real platforms too.

Appendix

Glossary

Every data engineering term the course uses, in one place. The lesson number says where it's taught.

Asset (Airflow) · L12
A named piece of data (here, an Iceberg table URI). A task that updates it emits an event, and a DAG scheduled on it runs. That is data-aware scheduling, as opposed to a clock.
Audit table · L8
A table that records what the pipeline did: runs, counts, statuses (audit.ingestion_runs, audit.ulog_downloads). It lets you answer "what happened?" with SQL.
Backfill · L9
Running a pipeline for past periods it missed or must redo. Here: trigger px4_ingest_daily with {"day": "…"}.
Batch processing · L1
Processing data in scheduled chunks (one day of uploads), as opposed to streaming each record as it arrives.
Bronze / silver / gold · L1, L11
The medallion layers. Bronze is raw data as received, append-only. Silver is cleaned, typed and modeled. Gold is aggregated tables for one use (a dashboard), with a fixed contract.
Catalog · L6
The service that maps a table name to its current metadata file and swaps that pointer atomically on each commit. Here, Lakekeeper.
Compaction · L15
Rewriting many small data files into fewer large ones, so queries open fewer files (Iceberg optimize).
Conditional GET · L3
An HTTP request with If-None-Match: <ETag>. The server answers 304 Not Modified with no body when the resource hasn't changed.
Data contract · L11, L13
A promise about a table's columns and types. dbt enforces it on gold, so the build fails instead of the dashboard breaking silently.
Dead-letter table · L8
Where records that fail validation go, with a reason, instead of crashing the load or vanishing (bronze.rejected_records).
DAG · L9
Directed acyclic graph: tasks plus the dependencies between them. In Airflow, a Python file that defines one.
Dimension / fact · L11
A fact table records events or measurements (one row per flight). A dimension describes the things they refer to (vehicle, date, flight mode). Together they form a star schema.
Dynamic task mapping · L9
Creating N copies of a task at run time from a list (one task per batch of ULogs).
ELT / ETL · L1
Extract-Load-Transform: land raw data first, transform it later with SQL in the warehouse. ETL transforms before loading.
Grain · L11
What one row of a table represents ("one flight", "one vehicle class per month"). Every aggregation question starts here.
Idempotency · L3, L8
Running the same step twice gives the same result as running it once: no duplicates, no harm. It makes retries safe.
Incremental model · L10
A dbt model that processes only new rows on each run (MERGE), instead of rebuilding from scratch.
Landing zone · L4
Object storage holding source files exactly as received, before any parsing. It's a replayable, auditable copy of the source.
Lakehouse · L1
Open table formats on cheap object storage, queried by SQL engines: warehouse features (tables, ACID, SQL) on a data-lake substrate.
Lifecycle rule · L4
An object-storage rule that deletes (or moves) objects after N days. It needs no job.
Lineage · L10
Which tables each table is built from. dbt derives it from ref() and source().
Manifest · L4
A small file written last that describes a landed batch (ETag, size, sha256). Its presence means the batch is complete.
Materialization · L10
How dbt persists a model: view, table, incremental, snapshot…
Orchestration · L9
Deciding what runs when, in which order, with retries and alerts. It doesn't do the work itself.
Partitioning · L5, L7
Splitting a table's files by a column's value (e.g. month of log_date), so a filtered query skips whole partitions (pruning).
SCD2 · L11
Slowly changing dimension, type 2: keep every version of a row, with valid_from / valid_to, instead of overwriting it.
Schema evolution · L5
Changing a table's columns (add, rename, widen) without rewriting its data.
Snapshot (Iceberg) · L5
The complete state of a table after one commit. Old snapshots enable time travel until they're expired.
Soft delete · L6
A dropped table is hidden but kept for a while (7 days here), so it can be restored.
Source freshness · L13
A check that the newest raw data is recent enough, so the pipeline doesn't publish yesterday's numbers as today's.
Table format · L5
A specification (Apache Iceberg here) that turns a folder of data files into a table with a schema, snapshots and atomic commits.
Time travel · L5
Querying a table as it was at an earlier snapshot.
